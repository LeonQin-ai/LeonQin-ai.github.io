# 从“回答完成”到“任务完成”：Agent 的状态、证据与故障恢复

> 一个 Agent 产品最影响信任的地方，往往不是答得不够流畅，而是状态与事实不一致：工作没做却显示完成，或者答案已经完整却显示失败。

这是 [Cognitive OS](https://github.com/LeonQin-ai/cognitive-os-agent) 技术系列第 6 篇。可靠性没有一个开关，需要在多个边界持续校验。

## 需要防止两种相反的错误

第一种错误是缺少执行证据。用户要求创建文件，模型只回答“我会创建”；或者要求完整阅读代码，模型只浏览了目录。这时不能把文本当成完成凭证。

第二种错误是过度纠偏。用户问“你的操作安全吗”，模型完整解释权限和风险，其中一句“如果你让我执行危险命令”包含“让我”。旧的意向检测在整段文本中匹配短语，误把条件说明当成未执行计划，重试后反而标记失败。

修复采用更明确的任务范围：独立的安全、权限、能力边界说明问答可以直接完成；匹配整个请求，追加“创建文件”“连接服务器”等操作后，就不再获得该豁免。原有文件读写与完成检查继续生效。

这种基于规则的判断仍有语言边界，不能被宣传为通用自然语言意图证明。它的价值是把已知误判变成清晰、可回归的正反例。

## 状态要能解释，也要能留下来

Scheduler 区分 QUEUED、RUNNING、DONE、FAILED、CANCELLED、TIMEOUT。前端展示的运行状态应来自任务实际生命周期，执行过程中的模型阶段与工具阶段属于更细的进度信息。

Runtime 还会把任务转移写入 journal。用户关心的不只是当前进程中的对象，而是重启之后能否知道：哪项任务正在执行、哪项已经终止、之前做到了哪一步。

在多 Agent 场景中，这个要求更明显。一个角色成功、另一个失败时，不能只因为“有人说话了”就把群讨论标成成功；依赖失败阻断的节点也需要与实际执行失败分开表示。

## 恢复首先要承认执行被中断

进程被强制终止，与一个工具正常返回错误不同。前者可能根本没有机会写最终状态。

项目的进程恢复测试会启动独立 Runtime，等待 RUNNING 任务和可用快照，强制终止该测试进程，再用同一状态目录启动。系统识别残留任务为 INTERRUPTED，之后显式恢复快照并重放适合的文件工作。

```text
RUNNING + 快照
 → 进程被终止
 → 重启识别 INTERRUPTED
 → 核对并恢复快照
 → 显式重放
 → DONE
 → 验证后续任务仍可运行
```

测试选择幂等文件替换，是为了让恢复后的结果可验证。任意 shell、SSH 或外部服务请求可能已经产生不可逆副作用，因此不能由这个实验推导所有外部操作都能自动重试、恰好执行一次，或保证断电耐久性。

## 事务和审计各自提供什么

文件事务与快照帮助恢复覆盖前的内容，审计和执行记录帮助追踪发生过什么。它们服务于不同问题，不能因为存在日志就认为可以撤销，也不能因为支持文件回滚就认为可以撤销一条远程命令。

SSH 还涉及密码处理。项目对 SSH 密码做专门保护，避免将其暴露为普通模型参数或命令行文本；这不意味着可以对任意字符串进行宽泛脱敏。普通 URL、文件路径和用户需要阅读的内容被误改，同样会破坏执行与排错。

## 完成判定应看作一组契约

“任务完成”不是单个统一条件。说明性问答、源码阅读、文件生成和发布操作，需要不同证据。把它们都简化为“模型返回了一段文字”，会误报成功；把它们都简化为“必须写过文件”，又会误报正常问答失败。

| 请求 | 合理的完成证据 | 单独不足以证明完成的信号 |
| --- | --- | --- |
| 解释权限机制 | 回答覆盖问题且没有待执行操作 | 出现过一次工具调用 |
| 完整阅读指定源码 | 明确范围与连续读取证据 | 枚举目录、看过 EOF 标记 |
| 生成 PPT | 本次产物、可打开的结构、内容核对 | 导入 pptx 库成功 |
| 修改并验证代码 | 相关修改、所要求的验证结果 | 只写了修改建议 |
| 执行远程动作 | 对应远程结果及其状态 | SSH 登录成功 |

当前实现利用用户任务、工具结果、待续读文件和意向检测等规则组合判断。它能纠正一些已知失败，但还不是通用的任务契约引擎。例如，成功运行一个只读 shell 探针，可能提供“运行过命令”的证据，却没有证明所请求产物已经生成。

因此我会把更严格的产物声明、版本关联和验证步骤视为后续可靠性方向。文章应保留这些不足，开发者才能判断系统在自己的任务里还需要补哪一层。

## 为什么最终兜底总结不能把失败变成成功

长任务可能达到规划轮数上限、重复计划而停滞，或连续工具失败。此时 Runtime 仍可用已收集观察生成一段工具不可用的总结，让用户了解进展。这个总结属于结果说明，不能反过来成为任务已完成的证据。

`reasoning.c` 因此区分正常最终回答与在预算耗尽等条件下触发的 synthesis。即使合成出了流畅文本，若原任务仍缺阅读、操作或验证，就保留未完成状态，并说明具体原因。

同理，“已经保存执行记录”是系统的恢复能力，不是用户任务的交付物。一次失败任务也可以有完整日志；日志存在，不应让前端写成工作已经完成。

## 取消、超时和进程崩溃是三类事件

取消来自用户或接管逻辑，超时来自时间预算，崩溃则可能让当前代码根本来不及返回。它们可以都导致任务不再继续，却具有不同的排查信息和恢复策略。

调度器的 `task_should_abort()` 检查取消标记及执行时间；工具和推理在相应位置响应。真正终止一个在途系统调用，还依赖底层进程与 HTTP 超时实现。UI 先展示取消意图，与后端已经完成清理之间可能存在时间差，应通过真实状态继续观察。

重启恢复则读取持久 journal。`tasklog_recover()` 按任务 ID 与记录顺序整理最后一次转移，把最后状态仍是 RUNNING/QUEUED 的任务追加为 INTERRUPTED，同时根据历史最大 ID 推进下一任务 ID，避免重启后 ID 被重新复用。

```text
id=41 QUEUED
id=41 RUNNING
    ← 进程在此被终止，没有最终记录
重启扫描：41 的最后状态仍在执行
id=41 INTERRUPTED
下一次新任务 ID > 历史已使用 ID
```

这里的目标先是恢复事实：上次执行中断了。系统没有资格在缺少外部证据时猜测“也许已经完成”，也不能直接宣布所有副作用都已撤销。

## 回滚、重试与幂等为什么不能混用

文件快照可以保存写入前的内容，事务失败时恢复本地受管理文件。外部 shell 或 SSH 可能已经发送请求、创建远程资源或修改另一套系统，这些副作用不一定处在本地快照覆盖范围内。

假设远程服务已经完成“扣款”，但响应在回程丢失。Runtime 只看到超时；盲目重试可能再次扣款。这是结果未知，而不是已知失败。要可靠重试，通常需要对方支持幂等键、可查询的业务操作 ID，或在重试前核对外部状态。

对于文件生成，也存在不同语义：把 `note.txt` 覆盖为固定内容通常可重复；向日志末尾追加一行、递增计数器或发一封邮件则可能重复产生效果。恢复测试选择固定文件替换，是为了把重放结果限制在可验证范围。

| 机制 | 核心问题 | 能直接推出的保证 |
| --- | --- | --- |
| journal | 上次执行处于何种状态 | 可追踪已记录的转移 |
| 快照 | 某些受管理文件原来是什么 | 可以按支持范围恢复 |
| 重试 | 是否再次执行 | 不能单独推出无重复副作用 |
| 幂等设计 | 重复请求怎样合并 | 取决于具体操作与外部系统 |
| 审计 | 谁在何时调用了什么 | 可排查，不等于可撤销 |

要讨论 exactly-once，必须明确业务边界、持久化原子性和外部协议。单机进程恢复实验不足以建立这个结论。

## 可观测性要能够串回一次执行

排查时至少要能把用户请求、任务 ID、会话、模型轮次、工具步骤和最终状态联系起来。同一个任务中，模型等待慢与工具运行慢需要分别计时；工具名相同但参数不同，也不能简单统计成同一个失败。

一个有用的事故记录可以采用下面的结构。这是整理日志的示意，不是当前 API 响应的字段承诺：

```json
{
  "build": "实际运行二进制的来源",
  "task": "任务 ID 与会话",
  "expectation": "用户要求的交付结果",
  "last_model_response": "最后一轮的格式与含义",
  "last_tool_result": "成功、失败、超时或根本未调用",
  "artifact_check": "产物路径、内容与本次执行的关联",
  "terminal_state": "Runtime 最终写入的状态"
}
```

这种记录能直接识别几类不同问题：计划没有被解析、工具返回失败、成功结果在后续处理中丢失、旧版程序未更新、完成规则没有覆盖该请求。只有一句“执行失败”通常无法区分它们。

## 如何把事故变成回归

我会先固定最小触发输入，再给外部依赖一个可控制的 fixture。对于提前结束，fixture 先输出读取计划、再输出错误的完成声明；测试必须确认 Runtime 要求继续或保留未完成。对于误报失败，则用完整说明性回答确认它不再被当作操作意向。

崩溃测试需要更高一层：启动自己拥有的独立进程，等待 RUNNING 与快照可用，强制终止，再用相同 state 重启。若仅调用某个“恢复函数”并传入静态数据，就测不到进程退出、日志落盘和重启初始化的组合边界。

测试也应避免用固定睡眠猜测时机。等待可观察状态后再终止，比“睡一秒然后 kill”更稳定；错误路径应保留日志，并让测试后续提交正常任务，确认恢复没有留下损坏的运行状态。

## 面试追问：可靠性做到哪一步

**有这么多检查，能否保证任务一定成功？** 不能。目标是让结果与事实尽量一致，失败可解释、进展可恢复；工具权限、外部系统和模型能力仍然决定任务是否可完成。

**状态中断后为什么不全部自动继续？** 因为有些外部效果未知，重放可能重复执行。先识别中断并让恢复范围可检查，比默认假设所有动作都可重试更稳妥。

**规则修复会不会引入新的误判？** 会。所以每个已知失败都应增加相邻反例，例如“解释如何创建文件”与“实际创建文件”，并检查混合请求。关键词规则始终要承认语言边界。

**如何评价未来的改进？** 除成功率外，同时统计误报成功、误报失败、重复副作用、取消完成时间和恢复后可继续运行的比例。只提高界面显示 DONE 的比例，可能让系统更不可信。
