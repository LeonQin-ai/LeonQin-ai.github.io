# 模型说要调用工具，Runtime 如何接住：协议解析、分页阅读与附件处理

> 一次工具调用失效，有时不是工具坏了，而是模型计划没有被正确解析；一次源码总结不完整，也可能是系统把“读了第一页”误当成“读完”。可靠执行需要把输入格式和完成证据都处理清楚。

这是 [Cognitive OS](https://github.com/LeonQin-ai/cognitive-os-agent) 技术系列第 5 篇，选三个实际工程问题说明模型输出如何进入执行链路。

## DSML 出现在答案里，却没有工具执行

用户曾遇到这样的记录：模型输出了多段 DSML 工具调用，界面却显示“本次未调用工具”。模型表达了动作，Runtime 没有把该格式还原为合法计划，自然也就没有真正执行。

Planner 因此需要兼容项目覆盖的 JSON、标签和 DSML 形式，将工具名与参数转换为内部动作数组。重要的不是“能从字符串中找到一个工具名”，而是整批计划中的每个动作都能正确恢复。

一个危险的折中是：某一段解析失败，就丢弃它，却仍把整项任务宣布完成。项目对 DSML 采用整批校验：非法或不完整结构需要明确失败，不能静默遗漏动作。JSON 截断的恢复策略另有处理，后文会区分这两条路径。

兼容解析也有边界。支持若干协议变体，不等于可以执行任意模型文本。结构合法之后，仍需工具查找、参数处理、策略与实际执行。

## 文件读取成功，不代表完整阅读成功

大型源码通常分多页读取。假设第一段已经成功返回，模型随即写出“项目完整分析如下”，Runtime 如果只看最后一句，就会提前结束。

项目的文件阅读链路会提供或追踪 `offset_bytes`、`next_offset_bytes` 和 EOF 等信息。对明确要求完整阅读的任务，未到 EOF 的文件属于尚未完成的工作；目录枚举也不能替代源码阅读。

```text
读取 source.c 的第一段
 → 发现还有 next_offset_bytes
 → 继续读取后续字节
 → 核对 EOF
 → 根据完整观察整理结果
```

偏移使用字节口径，后续页应沿工具返回的偏移继续，而不是自行根据显示行数推算。模型请求过大的页长时，系统还需要明确说明实际截断值，避免“请求读很多”和“实际只拿到一部分”之间出现静默差异。

相关 HTTP 回归会把关键证据放在文件末段，再确认模型实际拿到该证据。只检查工具返回过 success，无法覆盖这个问题。

## 支持附件，需要区分三层能力

用户上传图片、Word、PPT、PDF 或视频时，至少存在三个不同阶段：接收与保存文件、提取可用表示、让模型理解这些表示。

项目在附件链路中记录类型及解析元数据；文档可提取文本，多模态内容可形成图片或视频采样帧等输入。视频帧理解属于采样观察，不能等同于完整逐帧理解，更不能据此宣称音轨转写、每个动作识别都已具备。

实际效果依赖格式、可选解析依赖和所用模型。扫描件可能需要 OCR，图片输入需要兼容视觉能力的模型接口，损坏文件或不支持的格式应该返回诊断信息。文件扩展名出现在列表里，不是解析质量的证明。

另一个边界是请求时间。图片解析或视觉模型迟迟不返回时，用户需要看到阶段、超时与错误，而不是无限等待。相关回归通过慢速本地 provider，验证超时后能结束，并能继续下一次正常请求。

## 一次 90 个动作的任务，为什么仍没有 PPT

这类问题在真实日志中出现过：用户要求整理技术项目的深度 PPT，任务运行 21 轮，记录 90 个工具动作，然后状态变成 DONE。拆开动作才发现，88 次是读取与检索，另外两次 shell 分别检查 `python-pptx` 是否可导入，以及列出现有产物文件。

最后一轮模型输出四个 `file_read` 的 DSML 调用。旧版程序紧接着写出 `no tool plan, treating LLM output as answer`，把待执行计划当成最终文字答复。目录里旧 PPT 的存在又容易造成错觉：有文件，不等于本次任务生成了文件。

排查得到两个不同层面的事实：源码中已经加入对应协议解析，但用户正在运行的仍是此前安装的旧二进制；另外，动作数量也没有提供产物完成的证据。修复协议后还需要更新实际运行程序，再用新的任务核对交付结果，不能因为单元测试能解析四个调用，就宣称真实 PPT 已生成。

这也是日志里应该带构建来源的原因。版本号可能未变化，源码分支也可能比安装包更新；定位时应记录可执行文件路径、构建时间或提交信息，并确认监听端口的实际进程。本文的案例只引用任务相关信息，没有必要公开用户模型配置或凭据。

## 从外部格式到内部动作数组

Planner 最终需要得到类似下面的内部含义：

```json
[
  {"tool":"file_read","args":{"path":"source.c","offset_bytes":0}},
  {"tool":"file_read","args":{"path":"notes.md","offset_bytes":4000}}
]
```

格式适配与工具执行应分开。适配器负责恢复工具名、参数对象和调用顺序；执行阶段负责查找工具、策略检查、运行、收集结果。即使格式解析正确，路径仍可能不存在，模型仍可能调用未知工具，网络仍可能失败。

DSML 支持不同竖线标记和参数形式；外层 calls/function_calls、invoke、parameter 的结构必须配对。`args` 或 `arguments` 作为对象封装时不能再混入冲突的散列参数。字符串中的类似标签内容也必须按负载处理，不能随意正则删除。

当前源码对顶层 DSML 响应采用完整校验，失败时明确返回错误。其他 JSON 格式存在截断修复与挽救前导完整动作的路径，不能把 DSML 的整批规则泛化成所有格式都保证原子执行；解析的一致性与执行事务的原子性也应分别讨论。

## 为什么不靠一个正则提取所有工具调用

工具参数可能包含嵌套对象、转义引号、代码正文，甚至含有看起来像闭合标签的文本。用“遇到第一个右花括号就结束”的匹配，会把合法内容截断。反过来，贪婪匹配又可能吞掉下一个调用。

更可靠的方式是识别协议边界，再让 JSON 解析器处理参数对象，明确区分字符串参数与结构参数。正则适合某些有明确边界的字段提取，不适合独自承担任意嵌套语言的解析。

另一个边界是示例文本。用户可能要求“解释这段 DSML”，附件可能只是文档里的工具示例。解析器只应处理符合预期位置的顶层计划，不能在任意正文中搜到一个 invoke 就执行它。源码测试也包含正文示例和 JSON 字符串内字面标签的情况。

## 中文源码分页，为什么偏移经常不是 4000 的整倍数

工具使用 4–4000 字节页长。中文 UTF-8 字符通常占多个字节，页尾可能落在字符中间。实现会尽量回退到完整字符边界，再返回实际读取长度，因此下一页起点可能是 3998、7998 等值。

```text
请求：offset_bytes=0，max_bytes=4000
实际：页尾回退到 3998 字节
返回：next_offset_bytes=3998

正确后续：offset_bytes=3998
错误后续：自行按请求页长推算为 4000
```

如果跳到 4000，就可能漏掉字节；如果反复从零读取，动作数会增加却没有扩大覆盖范围。超大 `max_bytes` 会被限制到实际页上限，后续仍必须使用返回值，不能按请求的大小推进。

追踪完整性还应关注连续覆盖。读了 `[0,3998)` 和 `[7998,EOF)`，即使后者显示 EOF，中间仍有缺口。Runtime 为待续读路径记录连续前沿，目的就是避免用“见过 EOF”替代“连续读到 EOF”。

这项机制也有明确边界：它跟踪读取动作与分页结果，不是文件系统的一致性快照。若文件在阅读期间被其他进程修改，还需要版本或内容校验才能证明读到的是同一个文件版本。这是进一步提高完整性保证时应补的条件。

## 附件处理的诊断树

面对“图片一直卡住”或“PDF 解析空白”，先定位层次，再换模型。可以按下面的路径排查：

| 层次 | 要观察的事实 | 常见误解 |
| --- | --- | --- |
| 上传 | 保存路径、大小、类型识别 | 接收成功就代表解析成功 |
| 提取 | 提取文本、页数或帧元信息、警告 | 扩展名在列表里就全部可读 |
| 输入组织 | 文本预览、原文件路径、图片/帧数 | 所有原文都已发送给模型 |
| Provider 请求 | 实际模型、超时、图片能力 | 模型名字像视觉模型就一定支持 |
| 完成核对 | 任务要求对应的输出与证据 | 给出一段总结就完成全部处理 |

PPT 文本提取不等于读取动画、图表和演讲者表达；扫描 PDF 的空文本可能是缺 OCR；视频采样帧可能遗漏采样点之间的事件。文章应描述已经拿到的表示，再说明由它能支持什么判断。

视觉等待还需要独立时间边界。当前请求有视觉专用超时设置，失败信息应说明模型与等待配置；超时后要释放当前任务状态，让后续正常请求仍可运行。只在前端显示“正在思考”，无法解释系统到底在等待提取进程还是 Provider。

## 以分层回归核对执行链路

协议回归先在解析层检查动作数、顺序和参数，再经过真实 Runtime 执行文件写入与读回，分别验证格式还原和执行连通性。

分页用例把唯一证据放在末尾，使提前结束能够被观察，同时核对连续偏移，避免模型直接跳读末段。只检查一次工具成功或最终回答中的标记，都不足以证明完整覆盖。

本地慢速 Provider 能控制响应延迟、错误和格式，稳定复现超时边界。真实远程接口的偶发响应适合兼容性观察，却难以作为每次都可重复的控制流测试。

## 怎样观察真实执行

我希望演示可以回答：模型发出了什么动作？Runtime 解析出了几个？实际工具是否调用？分页是否结束？失败是哪一层产生？

在构建 CLI 后，可从这些回归进入：

```bash
cd backend
python tests/test_dsml_e2e.py
python tests/test_source_read_e2e.py
python tests/test_vision_wait_e2e.py
```

这些用例使用本地模型 fixture 和真实 Runtime/API，验证协议与控制流；它们没有测量生产模型对所有文件的理解准确率。
