# 让多个 Agent 真正讨论起来：从逐个回答到有界多轮协作

> 把两段角色提示词放在一个群里，未必就形成了讨论。真正的交互需要让先发言的人有机会回答后来提出的问题，也需要明确何时结束、如何停止，以及新消息到来后旧答案该怎么办。

这是 [Cognitive OS](https://github.com/LeonQin-ai/cognitive-os-agent) 技术系列第 2 篇，记录群聊从单轮回复升级到多轮讨论的实现。

## 一次遍历为什么不够

旧实现按成员列表依次调用 Agent。假设群里有架构师 alpha 和评审 beta：alpha 先提出方案，beta 读取方案并提问，随后任务结束。beta 看到了 alpha，alpha 却没有机会看到 beta 的问题。

这不是模型不会交流，而是调度过程没有安排下一次发言。

现在，群聊默认执行 3 轮，每轮按成员顺序发言：

```text
第 1 轮：alpha 提出方案 → beta 提出疑问
第 2 轮：alpha 回答疑问 → beta 核对并补充
第 3 轮：alpha 修正结论 → beta 说明剩余取舍
```

轮数可以设置为 1–5。选择 1 轮时仍是原先的逐个回复方式。

## 让“讨论”落到输入里

每次发言都包含角色身份、成员列表、当前轮次、最新群记录和原始用户目标。群记录以带 `speaker`、`role`、`content` 的 JSON 传入，原始用户请求单独放在 `## 用户任务` 段落。

第一轮提示角色提出观点和具体问题；之后要求回应其他成员、检查假设、完善已有方案。Runtime 为每个房间与角色隔离会话状态，同时每次重新读取房间记录，避免只依据自己上一次说的话。

当前上下文最多取最近 128 条房间消息，原始用户目标另外保留。因此它不是无限历史，也不是所有角色始终拥有完全相同的记忆。长对话仍受到模型窗口、检索和概括质量的影响。

## 讨论必须有结束条件

最确定的边界是轮数上限。另一个可选信号是 `[[DISCUSSION_DONE]]`：角色可以在回复末尾附上它，表示自己没有新的问题或补充，并同意结束。

只有同一完整轮次中所有成员都给出这个信号，才提前结束。某个角色单方面说“结束”不能跳过其他成员。标记会在入群前移除，不混入面向用户的正文。

这个机制表达的是结束讨论的协调意愿。两个模型都赞成某个方案，不等于方案经过测试，更不能替代实际工具结果或人工评审。

## 新消息到来，旧答案不能继续刷屏

一个容易忽略的场景是：模型还在生成时，用户已经补充了新要求。

实现分成两层。首先，新消息派发时，会给该房间正在执行的旧任务设置取消标记，让推理循环也知道旧任务已被接管。其次，Agent 回复入库时，在 IM 存储锁内再次检查：触发这次回复的用户消息，是否仍是房间最后一条用户消息？

```text
检查最新用户消息 → 追加 Agent 回复 → 保存
                 同一个存储锁
```

如果期间出现新用户消息，就拒绝写入旧回复。仅在模型调用前检查一次是不够的，因为生成结果回来时，讨论条件可能已经改变。

Agent 回复只追加和广播，不会再次自动派发一个新任务。多轮循环由 Runtime 显式管理，最多 5 轮，不会因为两位角色相互回复而无限递归。

## 一次两人讨论，具体共享了什么

用一个具体问题观察输入，比只看最终聊天记录更有用。用户要求讨论“文件读取完整性验证”，alpha 第一轮提出“按路径记录 EOF”，beta 随后追问“文件读取期间发生修改怎么办”。第二轮 alpha 的请求中应包含这条追问，alpha 才可能承认原方案缺少版本约束。

下面是用于理解的上下文示意，不是额外的 API 格式：

```text
角色：alpha，负责提出实现并回应评审
成员：alpha、beta
当前轮次：2 / 3
最近房间消息：
  user: 讨论文件读取完整性验证
  alpha: 按规范路径跟踪连续偏移与 EOF
  beta: 如果读到中途文件被修改，EOF 能证明什么？
## 用户任务
讨论文件读取完整性验证
```

这种组织同时解决“看得到别人”和“知道自己在完成什么”。如果仅把房间消息拼成一句连续文本，角色身份和消息来源容易混淆；如果把整个群记录都当作完成要求，beta 的建议又可能被误当成用户已经授权的操作。

结构化消息改善了来源表达，但它不是对提示注入的完整防护。角色仍可能被文本中的伪指令影响。更可靠的执行范围还需要由工具策略、节点原始任务和实际权限共同限制。

## 顺序发言与并行发言，选哪一种

当前实现每一轮按成员顺序发言。优点是本轮后发言者能直接看到前面刚产生的结果；代价是后者的延迟叠加到整轮时间里，且先发言的观点可能影响后面的角色。

假设有 N 位角色、最多 R 轮，每次发言平均耗时 L。在没有提前结束和额外工具轮次的理想化估算下，串行发言的时间约为 `N × R × L`。若每次回答本身还触发多个工具规划轮，真实时间会更长；这不是一次单纯的 N 次 API 批量请求。

并行发言也有自己的成本：同一轮所有人读到相同快照，无法回应本轮刚刚产生的问题；通常要增加一个汇总或下一轮才能交换意见。因此“同时调用更多模型”不必然更快得到稳定结论，应该比较达到同等证据质量所需的总轮数和 token 成本。

| 组织方式 | 本轮能否看到刚产生的意见 | 适合的任务 | 需要承担的成本 |
| --- | --- | --- | --- |
| 当前顺序多轮 | 后发言者可以 | 追问、方案修正、面试模拟 | 延迟累加、顺序影响 |
| 同快照并行评审 | 通常不能 | 独立找风险、盲评 | 冲突要另行合并 |
| DAG 分工 | 取决于依赖边 | 阅读、修改、验证等交付链 | 要明确输入输出与失败传播 |

这里没有把三种方式合并成一个万能调度器。选择哪种组织方式，应由问题需要的交互关系决定。

## 迟到回复为什么需要二次校验

可以把触发讨论的用户消息 ID 理解为这次执行所依据的版本。执行开始时记住它，提交回复时再比较。关键时序如下：

```text
T0：用户消息 U1 触发 alpha
T1：alpha 的模型请求正在等待
T2：用户追加 U2，接管讨论
T3：U1 对应的模型结果返回
T4：存储锁内比较最新用户消息，发现是 U2
T5：拒绝追加 U1 的迟到结果
```

取消标记负责让旧任务尽快停止，存储锁内的校验负责阻止旧结果越过提交边界。两者补足的是不同的窗口：取消可能无法立即中断在途 HTTP 请求，而提交校验也不会节省旧请求已经消耗的 token。

这与数据库里的“读到版本后，写入前确认版本仍有效”有相似之处。这里的版本语义限定在房间的触发消息，不应把它扩展为整个系统的分布式事务保证。

## 收敛信号应该怎样解释

`[[DISCUSSION_DONE]]` 必须位于角色回复末尾，并由同一轮所有参与者共同给出。假设 alpha 第一轮认为可以结束，beta 却提出新问题，这一轮就不能算全员同意。Runtime 继续安排发言，让 alpha 有机会回应。

但全员同意仍可能是“共同接受了错误假设”。针对技术评审，我更希望角色把结论分成三类：已有工具证据支持、仅有推理支持、尚未验证。结束标记表达的是不再继续讨论，不能把后两类自动升级成已经验证。

一个更有用的讨论题是“请给出证据和可推翻该方案的反例”，而不只是“请评价这个方案”。前者能促使角色讨论失败条件；后者容易产生连续赞同。这个建议属于任务设计，不是当前 Runtime 自动具备的质量评分能力。

## 怎样证明角色确实互相回应

回归中最关键的断言不应只是“最后有六条 Agent 消息”。六条消息也可能是六段互不相关的介绍。应让 fixture 产生可识别的问答标记，并检查它们进入后续请求：

1. alpha 第一轮给出假设 A，beta 必须在输入中看到 A。
2. beta 输出问题 Q，alpha 第二轮的模型输入必须包含 Q。
3. alpha 输出回答 R，beta 后续输入必须包含 R。
4. 提交 U2 后，U1 的在途结果不得进入房间。
5. 停止后不再追加新回复，整体状态与取消或失败一致。

这些断言把上下文传播与语言质量分开测量。fixture 验证前者；要评价后者，还需要真实模型、固定题集、人工标准，以及事实错误率、未回应问题数、结论依据等评价维度。

## 面试追问：一位角色失败怎么办

**已经有人回答，整场讨论能否算成功？** 不能直接这样决定。某位角色网络失败时，用户需要看到这场讨论没有完整执行，以及哪些回答已经保留。已有内容有价值，与整体执行成功是两个判断。

**为什么不让 Agent 消息再次自动触发其他 Agent？** 那会形成回复触发回复的递归链，难以统一控制上限、取消和成本。当前多轮逻辑由一个显式循环管理，Agent 回复负责入库和广播。

**128 条消息以后会怎样？** 最近消息窗口会限制可见历史，原始用户目标另行保留。不能假设所有早期论据都仍在输入里。长讨论需要更精确的证据选择和摘要，但摘要也应保留来源与不确定项。

**为什么不直接把模型放在同一个会话里？** 独立角色会话能保留角色自己的过程，房间记录负责交换意见；混成一个会话容易把不同角色的工具结果和意图混在一起。隔离也增加了管理成本，需要明确哪些知识共享、哪些上下文仅属于当前角色。

## 如何体验与验证

先通过界面或 `/v1/agents` 注册角色，再创建群聊：

```json
{
  "name": "架构评审",
  "kind": "group",
  "members": ["alpha", "beta"],
  "discussion_rounds": 3
}
```

向 `POST /v1/im/sessions/<id>/messages` 提交话题即可开始。左侧显示角色和轮次，停止按钮调用 `DELETE /v1/tasks/<task_id>`。成员和轮次设置可一起修改，运行中的讨论使用启动时的设置快照。

回归用例用本地确定性模型实际检查：beta 的问题是否进入 alpha 第二轮输入；alpha 的回答是否进入 beta 的下一次输入；取消或接管后是否丢弃迟到结果；部分角色失败是否让整体如实失败。它验证交互管道，真实讨论深度仍取决于模型和问题。
